# 7. IPv6 Static Routes

Chapters 1 to 6 used IPv4, but nearly everything carries over to IPv6 unchanged: longest-prefix match, administrative distance, floating routes, tracking, discard routes. What changes is how you name the next-hop. IPv6 gives every interface a link-local address, and that small detail produces the most common IPv6 static routing error.

## Dual-Stacking the Lab

We'll add IPv6 to the same topology, using the `2001:db8::/32` documentation range:

| Segment | IPv6 prefix | Addresses |
|---|---|---|
| Branch LAN | `2001:db8:20:1::/64` | BR1 `::1`, SRV1 `::10` |
| BR1–HQ1 link | `2001:db8:0:12::/64` | HQ1 `::1`, BR1 `::2` |
| HQ LAN | `2001:db8:10::/48` (one /64 used) | HQ1 `::1` |

The branch owns `2001:db8:20::/48` overall, which leaves room to add more /64s later.

One IOS prerequisite first: Cisco routers don't route IPv6 until you enable it.

```text
BR1(config)# ipv6 unicast-routing
```

Forget this and the router behaves like an IPv6 host: it won't forward IPv6 packets between interfaces, whatever routes you configure.

## The Core Concept: Global vs Link-Local Next-Hops

Every IPv6-enabled interface has a **link-local** address in `fe80::/10`. Link-local addresses are only valid on their own link, and every interface on the router has one in the same range. So the router can't tell from `fe80::1` alone which interface that neighbor sits on.

That gives you two ways to write the next-hop:

### Global Next-Hop

```text
BR1(config)# ipv6 route 2001:db8:10::/48 2001:db8:0:12::1
```

It works exactly like IPv4: the router resolves `2001:db8:0:12::1` recursively through the connected `/64` (see [chapter 2]({{ '/docs/static-routing-first-static-route/' | relative_url }})).

### Link-Local Next-Hop (Interface Required)

```text
BR1(config)# ipv6 route 2001:db8:10::/48 GigabitEthernet0/0 FE80::1
```

The exit interface is **mandatory** here: it tells the router which link the `FE80::1` neighbor is on. Leave it out and IOS refuses the command and asks you for an interface. This is the fully specified form from chapter 2, and for link-local next-hops it isn't optional.

Why use link-local at all? Routing protocols already do (OSPFv3 and IS-IS next-hops are link-local), and your static routes keep working even if the link's global prefix gets renumbered.

### Pin the Neighbor's Link-Local Address

By default, a link-local address is generated automatically, often from the MAC address or randomly. Replace HQ1's hardware and its link-local address changes, which silently breaks every static route pointing at the old one. Set it by hand on the routers that act as next-hops:

```text
HQ1(config)# interface GigabitEthernet0/0
HQ1(config-if)# ipv6 address FE80::1 link-local
HQ1(config-if)# ipv6 address 2001:db8:0:12::1/64
```

Now `FE80::1` on Gi0/0 is a stable, readable next-hop.

## Hands-On: The Branch, IPv6 Edition

On BR1, a default route and a discard route for the branch range (the same pattern as [chapter 6]({{ '/docs/static-routing-discard-routes/' | relative_url }})):

```text
BR1(config)# ipv6 route ::/0 GigabitEthernet0/0 FE80::1 name V6-DEFAULT-TO-HQ
BR1(config)# ipv6 route 2001:db8:20::/48 Null0 name V6-BRANCH-DISCARD
```

On HQ1, the return route to the branch:

```text
HQ1(config)# ipv6 route 2001:db8:20::/48 GigabitEthernet0/0 FE80::2 name V6-TO-BRANCH
```

(This assumes you've also pinned BR1's link-local to `FE80::2`.) Floating routes work the same as in IPv4: append the administrative distance, for example `ipv6 route ::/0 GigabitEthernet0/3 <next-hop> 250`.

### SRV1: A Static IPv6 Default on a Linux Host

Most hosts learn their IPv6 default router from Router Advertisements (more on that below). Servers that need a fixed, predictable config get a static one. Pin BR1's LAN link-local address first (`ipv6 address FE80::1 link-local` on Gi0/1), then on SRV1:

```bash
sudo ip -6 route add default via fe80::1 dev eth0
```

Same rule as on the router: a link-local `via` needs `dev`. In Netplan, add `- to: "::/0"` with `via: "fe80::1"` under `eth0`'s `routes:`. Netplan knows which interface it belongs to from where you put it.

## Gotchas and Edge Cases

- **IPv4 and IPv6 are separate routing tables.** An IPv4 default doesn't help IPv6 traffic. Every route, every floating backup, every IP SLA probe has to be built twice on a dual-stack network. A failover that works for IPv4 but leaves IPv6 pointing into a dead ISP is common, and many browsers try IPv6 first, so users will notice.
- **A static default plus Router Advertisements means two defaults.** If SRV1 has a static IPv6 default and still accepts RAs, it ends up with a second, RA-learned default route. If you want the static config only, turn RAs off on that interface (`net.ipv6.conf.eth0.accept_ra=0`, or `accept-ra: false` in Netplan).
- **Exit-interface-only routes have the same problem as IPv4.** Without a next-hop, the router does Neighbor Discovery for every destination instead of ARP, which depends on the neighbor answering for addresses that aren't its own. Use a next-hop.
- **Hosts often don't need static IPv6 routes at all.** Router Advertisements give them a default router automatically. Static routes belong on routers and on servers with unusual multi-homing needs.

## Key Takeaways

- All IPv4 static routing concepts carry over: longest-prefix match, AD, floating routes, discard routes.
- Link-local next-hops require an exit interface, on IOS routers (`GigabitEthernet0/0 FE80::1`) and Linux hosts (`dev eth0`) alike.
- Pin link-local addresses on next-hop routers so hardware swaps don't break routes.
- IPv4 and IPv6 are configured, failed over, and tested separately.
